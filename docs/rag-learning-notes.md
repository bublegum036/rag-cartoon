## 1. Что делает RAG

RAG — Retrieval-Augmented Generation: перед формированием ответа система
извлекает сведения из своего источника и передаёт их модели как контекст.
В нашем проекте источник — [catalog.json](../catalog.json) с 12 вымышленными
фильмами. Факты об актёрах, рейтингах и возрастных ограничениях в нём отсутствуют.

Качество состоит из двух самостоятельных частей: нашёл ли поиск нужные факты
и правильно ли генератор ответил по ним. Хороший генератор не восполнит
отсутствующий в контексте факт. Хороший поиск тоже не исключает ошибку ответа.

В нашем решении RAG не обучает веса генератора на каталоге. Новые факты
поступают через обновление каталога и индекса. Embedding-модель отвечает
за векторы для поиска, генератор — за текст ответа; это разные зависимости.

## 2. Два потока данных

Индексация:

```text
Каталог → проверка и выбор активных ревизий → части описания
  → название + текст части → embedding-модель → EmbeddingBatch
  → новая коллекция Qdrant → проверка загрузки → переключение alias
```

Поток полного RAG в `ask`:

```text
Вопрос → план запроса
  ├─ требуется уточнение → clarify
  ├─ нужных сведений нет в схеме → insufficient
  ├─ смысловой поиск с фильтрами → части → группировка по фильму
  └─ точный факт / сравнение / подсчёт → операция над каталогом
        → контекст и вычисления → генератор → проверка → ответ
```

Сейчас `search` выполняет поиск с явными флагами. Команда `plan` отдельно
разбирает вопрос ограниченной грамматикой на правилах; она не запускает
полный RAG. Точные операции реализованы в `JsonExactCatalog` и доступны через
`exact`; `ask` соединяет планирование, поиск/вычисления и Gemini.
Порты описывают границы, а `bootstrap.py` выбирает реализации и проверяет снимки.

## 3. Карточки, части и источники

| Значение | Пример | Назначение |
| --- | --- | --- |
| `movie_id` | `film-01` | Узнать один фильм среди разных частей |
| `source_id` | `film-01#plot` | Ссылка на исходную карточку и сопоставление с эталоном |
| `chunk_id` | `film-01#plot:part-1` | Идентификатор конкретной части |
| `version` | `1`, затем `2` | Ревизия карточки |
| `active` | JSON `true` или `false` | Признак активности |

Короткие описания оставляем целиком. Длинные разбиваем по предложениям;
слишком длинное предложение — по словам. Не дополняем маленькие карточки
до фиксированного размера. Каждая часть сохраняет связь с исходной карточкой.
Код: [ingestion.py](../src/cartoon_rag/ingestion.py).

В embedding-текст всегда добавляем название. Найденные части объединяем
по `movie_id`, иначе один фильм может занять несколько мест в рекомендациях.

Лимит разбиения в символах — эвристика, а лимит модели измеряется в токенах.
Поэтому адаптер дополнительно проверяет токенизированный вход, включая
название и префикс. Переполнение отклоняется вместо молчаливого усечения текста.

## 4. Векторы и смысловой поиск

Embedding-модель преобразует текст в числовой вектор. Близость векторов
используется для отбора кандидатов со схожим смыслом. В нашем адаптере
`intfloat/multilingual-e5-small` используются префиксы `passage:` для документов
и `query:` для запроса. Код: [fastembed.py](../src/cartoon_rag/adapters/fastembed.py).

`score` — оценка близости в выбранной модели и метрике, а не вероятность
правильного ответа. Top-k возвращает ближайших кандидатов; это само по себе
не доказывает, что в каталоге есть ответ на вопрос.

Одинаковая размерность не делает векторы разных моделей совместимыми.
`EmbeddingBatch` передаёт векторы вместе с `EmbeddingIdentity`: провайдером,
моделью, ревизией, размерностью, версией реализации и способом кодирования.
Qdrant проверяет этот идентификатор до записи и берёт metadata из проверенного
пакета. Проверка нужна даже для пустого снимка. Изменение модели требует
переиндексации.

## 5. Тема запроса и строгие ограничения

В вопросе «про море и дружбу, короче 90 минут» тема задаёт смысловое
ранжирование, а длительность — точное условие `duration_minutes < 90`.
Фильтр должен применяться в базе до ограничения top-k. Если сначала выбрать
top-k без фильтра, подходящие фильмы могут остаться за его пределами;
удаление длинных фильмов из уже полученной выдачи их не вернёт.

По каталогу «Маяк для кита» длится 78 минут и проходит `< 90`,
«Коралловая почта» — 96 минут и не проходит. Ровно 90 не проходит `< 90`,
но проходит `<= 90`. Исходные факты: [catalog.json](../catalog.json).

Вопрос «Подойдёт ли Коралловая почта, если у меня 90 минут?» требует другого
маршрута: найти названную карточку и вычислить `96 − 90 = 6`. Если бюджет
превратить в поисковый фильтр, нужная карточка исчезнет и объяснить отказ
будет нечем. Намерение вопроса определяет операцию.

Подсчёты выполняем по полному подходящему набору, а не по количеству top-k.
Точные операции выполняет `JsonExactCatalog` через порт `ExactCatalog`.
Он использует весь подходящий активный снимок, а не семантический top-k.

## 6. Ревизии и публикация индекса

Сначала выбираем максимальную `version` фильма, затем учитываем `active`.
Если последняя версия неактивна, старую активную версию не возвращаем.
Учебный пример: film-01 меняется с 78 минут в версии 1 на 92 в версии 2.
После публикации версии 2 фильтр `< 90` должен исключить фильм.
Изменение проверяется на временных данных, исходный каталог сохраняется.

Новый снимок загружается в отдельную коллекцию. После проверки количества
точек переключается alias. Незавершённая загрузка не должна становиться
доступной поиску. Старые коллекции пока сохраняются; для долгой эксплуатации
потребуется политика хранения.

Таймаут переключения неоднозначен: операция могла успеть примениться.
Поэтому нельзя сразу удалять новую коллекцию как якобы неиспользуемую.
Код: [qdrant.py](../src/cartoon_rag/adapters/qdrant.py).

`PublicationResult` возвращает результат публикации через `IndexWriter`
и `index_catalog`. CLI не читает служебное состояние конкретного хранилища.

`RetrievalService` используется CLI и RAG-сценарием: группировка и проверки
имеют одну реализацию. `SearchService` добавляет планировщик, точные операции,

Аннотации dataclass и `Protocol` описывают контракт для разработчика
и инструментов проверки типов. Они сами не валидируют JSON при выполнении.
Важные инварианты проверяем явно и закрепляем тестами.

## 8. Ответ, отсутствие сведений и сбой

| Результат | Пример | Поведение |
| --- | --- | --- |
| `answered` | Девочка и кит чинят маяк | Ответ со ссылкой на подтверждающую карточку |
| `insufficient` | Кто озвучивает девочку? | Сообщить об отсутствии этих сведений в каталоге |
| `clarify` | «Сколько он длится?» без выбранного фильма | Уточнить название |
| Ошибка инфраструктуры | Таймаут Qdrant | Передать отдельную техническую ошибку |

Таймаут ничего не говорит о наличии фильма, поэтому его нельзя превращать
в `insufficient`. Существующая ссылка тоже не доказывает правильность текста:
структурная проверка источников и смысловая проверка утверждений различаются.

## 9. Оценка качества и A/B

В [questions.jsonl](../questions.jsonl) есть 10 случаев с ожидаемым статусом,
источниками, фильтрами и rubric. Эталон нужен оценщику. Планировщик
и генератор не должны получать ответы и ограничения из разметки.

```text
Recall@k = число найденных эталонных источников / число эталонных источников
```

Части сопоставляем с исходными `source_id`. Две части одной карточки не дают
два разных релевантных источника. В текущем коде k ограничивает части,
а не число фильмов; для точного маршрута учитываются извлечённые карточки.
Случаи без эталонных источников исключаем из среднего Recall@k.

Отдельно оцениваем долю принятых ответов и соблюдение строгих фильтров.
Ответ принимается по статусу, rubric, фактам, ограничениям и ссылкам.
Совпадение одной строки недостаточно. Альтернативную рекомендацию в открытом
запросе проверяем по тем же критериям. `ReviewedSemanticJudge` загружает явные
решения оценщика, проверяя их привязку к конкретным rubric и trace; он сам
не определяет смысловую истинность. Код: [evaluation.py](../src/cartoon_rag/evaluation.py).

Проверяем эталонные фильтры также в `trace.retrieved`, даже при правильном
ответе. Иначе потерянное планировщиком ограничение останется незамеченным.
Пустая выдача не нарушает фильтр, но сама по себе не доказывает качество поиска.

Порядок A/B: выполнить реальный A, сохранить найденные ID, контекст и ответ;
выбрать наблюдаемую ошибку; изменить один элемент; повторить те же вопросы
в B и сравнить метрики. Вымышленные результаты и заранее заданный успех
не заменяют эксперимент.

## 10. Уроки из наших ревью

| Ошибка или слабое место | Последствие | Исправление и вывод |
| --- | --- | --- |
| Фильтры проверялись только в рекомендациях | Поиск возвращал 96 минут при `< 90`, но ответ принимался | Проверять все найденные части по эталонным ограничениям |
| JSON `"active": "false"` проходил через dataclass | Непустая строка считалась истиной, карточка оставалась активной | Принимать только boolean; аннотация не заменяет валидацию |
| Векторы A подписывались metadata модели B | Поиск смешивал разные векторные пространства одной размерности | Передавать идентификатор с векторами и проверять до записи |
| CLI читал `store.last_publication` | Транспорт зависел от внутреннего состояния адаптера | Возвращать `PublicationResult` через контракт |
| Группировка дублировалась в CLI и RAG | Поведение могло разойтись | Использовать общий `RetrievalService` |

Первые три пункта — воспроизведённые дефекты. Последние два были
архитектурными улучшениями без подтверждённого сбоя на тот момент.

### Чистая установка из lock (25 октября)

выполняет pip-tools 7.6.2. Сначала загружаются подходящие wheels, затем
их хеши рассчитываются локально: это избегает скачивания пакетов других

### Планирование запроса на правилах (25 октября)

Принцип: план запроса отделяет смысловую тему от точных условий и определяет,
какое вычисление нужно выполнить. Он ещё не является найденным свидетельством
или готовым ответом. Ошибка в выборе маршрута может сделать нужный факт
недоступным генератору даже при правильном индексе.

Адаптер `RuleBasedQueryPlanner` реализует `QueryPlanner` и получает только
активные `movie_id` и названия. Он не знает фактов карточек или эталонов.
Команда `plan` показывает разбор без базы, embeddings и `.env`.
Новые языковые конструкции можно добавить в правила или в другой адаптер,
не меняя `SearchService` и порт планировщика. Новых зависимостей нет.

«Про море, короче 90 минут» даёт `SEARCH` с `< 90`, а условие удаляется из
текста для смыслового ранжирования. «Не больше 90» даёт `<= 90`.
Для вопроса про названную «Коралловую почту» при бюджете 90 минут выбирается
`COMPARE_DURATION`: ID остаётся, фильтра длительности нет. Только будущая
точная операция должна узнать 96 минут и вычислить разницу. Планировщик
не подставляет это число из каталога.

«Сколько фильмов короче 90?» даёт `COUNT`. «Сколько про море?» требует
уточнения: без точного тематического предиката нельзя выдавать количество
найденных векторов за количество всех подходящих фильмов.
«Короче 40» остаётся фильтром, а не ранним `insufficient`: наличие результатов
ещё не проверено. Вопрос про озвучивание получает `insufficient` на основании
отсутствующего поля схемы; «Сколько он длится?» — `clarify` без выбранного фильма.

Разбор ограничен целыми минутами и перечисленными в README формами.
Неизвестные/склонённые названия в кавычках, часы, дроби, нижняя граница
и неоднозначные числовые условия требуют уточнения. Слова и числа внутри
распознанного названия маскируются до разбора: «Рейтинг 90 минут» не должен
становиться фильтром длительности или отказом из-за отсутствия рейтинга.
Фраза «путешествие за 80 минут» без признака бюджета также требует уточнения:
время событий сюжета и длительность просмотра — разные ограничения.

Что проверено: 22 новых теста с перефразировками, граничными значениями,
маршрутами, активными версиями названий и CLI. Всего 63 теста прошли
с настоящими Qdrant/E5; в семантическую проверку добавлена передача плана
из текста в поиск с `< 90`. Все 10 исходных вопросов проверены по маршрутам,
планы сохранены отдельно. Это не приёмка ответов по rubric и не A/B.
Журналы: [этап планировщика](../artifacts/planner-verification-2026-10-25/README.md).

Осталось непроверенным: произвольная русская грамматика, фактические подсчёты
и сравнения, генерация и полная оценка. Следующий этап — `ExactCatalog`
поверх актуального снимка JSON, затем генератор, `ask`/`evaluate` и A/B.

### Исправления ранних отказов после ревью (25 октября)

Принцип: ранний отказ останавливает извлечение контекста. Поэтому совпадение
слова с названием поля недостаточно: нужно различать запрашиваемый факт,
ограничение и тему сюжета. Иначе работающий индекс вообще не получает запрос.

Первый подтверждённый дефект: «Сколько минут длится „Маяк для кита“?»
останавливался на проверке слова «минут». Теперь узнаваемая фраза запроса
длительности маскируется только при проверке оставшихся ограничений.
План выбирает `LOOKUP`, а `SearchService` обращается к каталогу. Единица
измерения в вопросе не задаёт верхнюю границу. Дополнительные числовые
условия по-прежнему проверяются; неподдерживаемая нижняя граница и секунды
не обходят валидацию. Добавлены кавычки `„…“` для точного названия.

возраста» получал `insufficient` из-за шаблона `возраст\w*`. Условие сужено

вопросительных форм. Тема возраста героев идёт в `SEARCH`. При этом поиск
сам по себе не доказывает нужный сюжет: генератор ещё должен проверить факты,

12 активных карточек и 10 вопросов; `git diff --check` прошёл.
Планы исходных 10 вопросов не изменились. Версия правил — `ru-rules-v1.1`.
Журналы: [исправления](../artifacts/planner-fixes-2026-10-25/README.md).

### Точный каталог (25 октября)

Принцип: векторная близость отвечает за кандидатов по смыслу, но не даёт
точного количества всех фильмов и не выполняет арифметику длительности.
Такие вопросы нужно направлять в операцию над полным проверенным набором.

`JsonExactCatalog` выбирает последнюю активную ревизию каждого фильма
и сохраняет неизменяемый снимок. Для `LOOKUP` возвращается полная карточка
со своим source_id. Для `COUNT` применяются точные фильтры ко всем карточкам;
для сравнения вычисляется «длительность − бюджет». Команда `exact` показывает
план, карточки и число, без генерации ответа, базы и embeddings.
Тот же `execute_exact` вызывается в CLI и `SearchService`, чтобы проверки
фильтров и источников не расходились между интерфейсами.

Подтверждённые примеры: в каталоге 12 фильмов, короче 90 минут — 9,
короче 40 — 0. «Коралловая почта» занимает 96 минут при бюджете 90:
разница +6. При бюджете 96 разница 0, при 100 — −4. Ни генератор, ни
семантический поиск не вычисляют эти значения. Контекст содержит карточки,
`chunks` пуст: точный источник не нуждается в выдуманном embedding-фрагменте.

Важное различие: нулевой подсчёт подтверждён полным проходом по снимку
и возвращает `ExactResult(0, "movies", ())`. Отсутствующая карточка для
lookup/сравнения возвращает `None`, а не нулевое число. Ошибка файла
или провайдера остаётся технической ошибкой и не доказывает отсутствие фильма.
При сравнении фильтр `< 90` запрещён: иначе карточка с 96 минутами исчезнет.

Что проверено: 21 новый тест, в том числе полный COUNT при лимитах поиска
и контекста 1, строгие границы `<`/`<=`, отсутствие дублей, версия 2 с 92 минутами,
неактивная последняя версия, недопустимые бюджеты, нулевой подсчёт и ошибки.
Проверены CLI и вызов точного адаптера через `SearchService`; генератор в этих
тестах — заглушка, его качество не оценивалось. Всего 85 тестов прошли,
3 интеграционных пропущены; `validate-data` и `git diff --check` прошли.
Журналы: [проверка этапа](../artifacts/exact-verification-2026-10-25/README.md).

Осталось непроверенным: реальные Qdrant/E5 повторно, генерация, полный RAG
и A/B. CLI использует один JSON-снимок для планирования и вычислений, но
не проверяет его совпадение с опубликованной коллекцией. При сборке полного
RAG потребуется сверка fingerprint JSON и metadata Qdrant перед использованием
двух источников. Далее — генератор структурированного ответа и эта сборка.

### Gemini и сквозной `ask` (25 октября)

Принцип: наличие правильного источника в top-k ещё не означает правильный
ответ. Генератор получает выбранные факты и должен отделить подходящие
карточки от похожих, а приложение проверяет структуру, ссылки и ограничения.
JSON-схема фиксирует формат; она сама по себе не доказывает истинность текста.

Подключён Gemini REST с моделью `gemini-3.1-flash-lite` и prompt
`grounded-ru-v1`. По выбору пользователя используется ключ проекта Free Tier;
тариф задаётся в Google AI Studio, приложение его не определяет.
Нет автоматических повторов, смены модели и платного fallback. HTTP 429,
таймаут и незавершённый ответ — технические ошибки `GenerationUnavailable`.
Ключ остаётся в `.env` и заголовке запроса; в JSON-контексте и трассах его нет.

Gemini получает только вопрос, план, выбранные карточки с частями и результат
точной операции. Системные правила отделены от этих данных. Для сравнений
передаётся вычисленное число, для подсчёта — полный точный результат.
Декодер не приводит неверные типы, не принимает неизвестные поля и проверяет
ссылки общей функцией `validate_answer`. Смысловая проверка остаётся отдельной.

Вторая граница — согласованность источников. Общий fingerprint активного
каталога используется при индексации и в `build_rag`. Прежде чем соединить
JSON и поиск, проверяется metadata Qdrant. Поиск закрепляется за физической
коллекцией, поэтому переключение alias не подменяет снимок внутри сервиса.
Тест настоящей базы подтвердил: после обновления alias старый закреплённый
поиск по-прежнему видит 78 минут, а попытка связать старый JSON с новым
снимком на 92 минуты завершается `SnapshotMismatch`.

Наблюдение из реального запроса «море и дружба, короче 90»: первым поиск
вернул film-11, затем film-01; все найденные карточки прошли фильтр.
В контексте из трёх карточек Gemini выбрал «Маяк для кита», указал 78 минут,
дружбу девочки и кита и `film-01#plot`. Первый кандидат сам по себе был бы
недостаточен; правильный ответ здесь опирается на отбор по смыслу из контекста.
Это наблюдение, а не оценка Recall@k на всём наборе.

Во втором запросе Gemini использовал готовую разницу `96 − 90 = 6`,
сообщил, что «Коралловая почта» не подойдёт, и сослался на `film-02#plot`.
Оба ответа просмотрены по фактам карточек, ограничениям и ссылкам.
Ранние `clarify` и отказ по озвучиванию получены без Gemini и базы.
В stdout сохраняется ответ, а `--trace` пишет отдельно план, найденное,
контекст, вычисление и ответ.

Что проверено: 18 новых тестов, всего 106 прошли с реальными Qdrant/E5;
проверки Gemini в этом наборе используют транспортную заглушку. Дополнительно
выполнены два настоящих запроса Gemini. `validate-data` подтвердил 12 карточек
и 10 вопросов; `git diff --check` прошёл. Новых Python-зависимостей нет.
Журналы: [Gemini и RAG](../artifacts/rag-verification-2026-10-25/README.md).

Осталось непроверенным: смысловая приёмка всех 10 готовых ответов, A/B,
поведение на произвольных вопросах и переносимость вне проверенной платформы.
Следующим этапом стали `evaluate` и реальные A/B, описанные ниже.

### Обрыв HTTP-ответа Gemini после ревью (25 октября)

Принцип: сбой получения свидетельства или ответа модели не является
свидетельством отсутствия фактов. Ошибки транспорта нужно преобразовывать
на границе адаптера, чтобы прикладной слой сохранял отдельную техническую ошибку.

Подтверждённый дефект: `json.load(response)` читает тело HTTP-ответа и при
преждевременном закрытии соединения получает `http.client.IncompleteRead`.
Это исключение не покрывалось прежним набором `OSError`/`URLError`/`ValueError`.
Новый обработчик `HTTPException` переводит его в `GenerationUnavailable`,
сохраняя причину через `__cause__`, не возвращая частичный ответ и не повторяя запрос.

Регрессия воспроизведена без сети: настоящий `HTTPResponse` получает из
`BytesIO` заголовок с `Content-Length: 100` и только 14 байт тела. До исправления
два новых теста падали с `IncompleteRead`. После исправления проверены
техническая ошибка адаптера, закрытие ответа, ровно один вызов транспорта,
а также путь через настоящий `SearchService` и CLI. В CLI stderr — JSON

### Evaluator и реальные A/B (25 октября)

Принцип: качество извлечения и качество ответа нужно оценивать отдельно.
Наличие эталонного источника в контексте не гарантирует, что генератор использует
нужный факт; увеличение top-k не исправит уже имеющуюся в контексте, но
пропущенную в ответе деталь.

`evaluate run` сохраняет все случаи и отдельные найденные ID/части, контексты,
ответы, trace и ошибки. В приложение передаётся только вопрос. До смысловой
разметки acceptance rate равен `null`. `evaluate score` работает офлайн:
решения связываются с хешами случая/разметки и ответа, старую разметку нельзя
молча применить к изменившейся trace. Статус и строгие фильтры проверяются
автоматически; смысл rubric, факты и поддержка ссылок требуют работы оценщика.
Здесь это просмотр Codex в сессии, не независимая человеческая комиссия.

В A все 10 случаев выполнились без технических ошибок. Recall@3 оказался
100%, но принято 9/10 ответов. В `space` источник film-03 был первым и находился
в контексте; ответ назвал правильный фильм, но не объяснил роль радиопередачи
в возвращении домой. Следовательно, проблема была в генерации/полноте ответа,
а не в поиске. Простое сравнение названия или source_id приняло бы этот ответ
ошибочно, проигнорировав rubric.

Изменили один элемент: к prompt v2 добавлено общее требование сохранять
конкретный способ решения сюжетной проблемы и причинную связь из карточки.
Название фильма, радиопередача и эталонная разметка в новый prompt не добавлялись.
Модель, индекс, планировщик, k, размер контекста, token limit и задержка те же.
Версия v1 сохранена для повторения, v2 стала значением по умолчанию.

В B `recommendations.reason` описал знакомую мелодию в радиопередаче и помощь
роботу с направлением домой. После просмотра всех ответов принято 10/10.
Recall@3 остался 100%, Recall@1 — 6/7 (85,7%), фильтры — 2/2 (100%).
Планы, найденные ID, контексты и точные вычисления совпали у A и B;
в runtime-конфигурации отличается только prompt version.

Для `no-match` общая фраза об отсутствии подтверждения запросу принята
семантически, без требования буквально повторить число 40: фильтр `< 40`
сохранён, альтернативных рекомендаций нет, в исходном каталоге минимум 52 минуты.

записях; 401/403/429 останавливают дальнейшие вызовы, а не ослабляют условия.
Проверены неполная разметка, stale-решения, отсутствие перезаписи и безопасные ID.

### Исправление метаданных генератора — 25 октября 2026

Воспроизводимый RAG-эксперимент требует записывать параметры фактически
использованного компонента. Настройки приложения не описывают объект, который
вызывающий код передал вместо штатного генератора: раньше prompt v1 и 128

по whitelist без сериализации транспорта и секретов. Штатный путь сохраняет
конфигурацию, с которой создаёт генератор.

Четыре новых теста проверяют обязательную identity, запрещённые сочетания,
штатную конфигурацию и сохранение параметров подмены в настоящем manifest
оценщика. Всего 124 теста прошли, 3 интеграционных пропущены; validate-data
подтвердил 12 карточек и 10 случаев. Gemini, Qdrant и E5 не вызывались.
Исторические A/B использовали штатный генератор и сохранены без изменений.

### Полный прогон расширения с Gemini v2 — 26 октября 2026

Качество извлечения, смысловая полнота ответа и доступность генератора —
разные свойства RAG. На 20 вопросах получены 16 ответов, все приняты при

с сохранением этого результата, затем внешняя смысловая проверка.

### Сохранение свидетельств до генерации — 26 октября 2026

Ошибки генератора не должны уничтожать наблюдаемость извлечения. Введён
PreparedQuery без поля ответа: prepare планирует, ищет или вычисляет точные
значения; answer использует уже подготовленные данные. Существующие ask
и execute_plan объединяют фазы, а evaluator записывает подготовку между ними.
Файловая система не стала зависимостью сервиса или адаптеров.

Новые прогоны имеют формат 2 и prepared_sha256. При сбое Gemini остаются
контекст, ID, фрагменты, план и вычисления; при ошибке записи генератор не
вызывается. Проверенный контекст не подменяет готовый ответ: приёмка остаётся
нулевой для технического сбоя, даже если Recall равен 1. Если потерян фильтр,
его нарушение видно и без ответа: проверяется каждый hit и карточка контекста
по независимым условиям случая.

Восемь новых тестов проверяют порядок записи при имитации HTTP 503 для
поиска и подсчёта, сбой поиска, отказ диска, подмену отдельных файлов,
расхождение между подготовкой и итоговой trace, независимые фильтры и
совместимость старых прогонов. Всего 132 прошли, 3 интеграционных пропущены;
validate-data прошёл для 12/10 и 40/20. Отдельный пример полностью офлайн:
два имитированных сбоя, две сохранённые подготовки, приёмка 0%, проверяемый
Recall 100%. Это демонстрация сохранности данных, не результат реального RAG.

Старые A/B и расширенный прогон проверены скорингом во временных копиях,
метрики совпали. Исторические исходники и результаты не переписывались.
Реальные Gemini, E5 и Qdrant для правки не вызывались. Следующий реальный
прогон сможет использовать новый формат, не теряя контекст при сбое модели.

Итог 3/4 → 3/4: единичное исправление не равно общему улучшению. Прочитаны

по удобному случаю. Четыре вызова Gemini завершились без технических ошибок;
Recall@1/@3 и фильтры 100%. Версия v3 сохранена для воспроизводимости,
по умолчанию остаётся v2. Полный набор 20 случаев с v3 не запускался.

Расширены существующие тесты неизменности остальных полей API-запроса
между всеми версиями, стабильности v2 и передачи v3 через CLI. 132 теста
прошли, 3 интеграционных пропущены; проверки данных прошли для 12/10,
40/20 и 40/4. Исторические прогоны и данные не менялись. Оценщик — Codex,
не независимый и не слепой; малый поднабор и вариативность API ограничивают
вывод. Следующая гипотеза — сохранять числовые факты ограничений при
расширении сюжета; она требует отдельной версии и проверки регрессий.

### Prompt v4 и ограничение проверки доступностью API — 26 октября 2026

Добавлена общая проверка, чтобы сюжетная полнота не вытесняла числа,
относящиеся к вопросу: длительность выбранного фильма и готовые значения
подсчёта/сравнения. Также запрещено выводить мотивы только из порядка
событий. v2 и v3 сохранены, остальные поля запроса и подготовки не менялись.

План предусматривал четыре прежних случая, затем все 20 при прохождении
первого этапа. В четырёх вызовах Gemini два HTTP 503 пришлись на sea-short
и count-all. Два полученных ответа (space и mechanical-whale) приняты;
общая приёмка 2/4 (50%). Сравнивать это с 75% v3 как ухудшение смысла нельзя:
в половине случаев нет ответа. Числовая регрессия sea-short остаётся
непроверенной. Полный этап не запускался; автоматического повтора не было.

Формат 2 сохранил все четыре подготовки, включая 78 минут с фильтром <90
и точный подсчёт 40 с полным контекстом. Recall и фильтры 100% подтверждают
данные извлечения, но не заменяют отсутствующий текст ответа. Так отделены
качество поиска, доступность генератора и смысловая приёмка. Ошибка API —
не доказательство того, что новый prompt исправен или ошибочен.

132 теста прошли, 3 интеграционных пропущены; расширены проверки всех
четырёх версий, стабильности старых prompt и CLI. Данные прошли валидацию
для 12/10, 40/20 и 40/4. Исторические прогоны не менялись; v2 остаётся
по умолчанию. Оценщик — Codex, не независимый и не слепой. Для следующего
реального эксперимента нужна доступность API, а не ещё одна правка текста
в попытке устранить HTTP 503.

### Повтор числовых случаев v4 — 26 октября 2026

Повторены только sea-short и count-all из технических ошибок предыдущего
v4. Runtime, prompt, вопросы, rubric и все подготовки совпали. Два вызова
Gemini завершились успешно; в sea-short есть 78 минут и сравнение <90,
в count-all — 40 со всеми 40 источниками. Числовая часть гипотезы подтверждена
на этих двух ответах, но устойчивость на полном наборе ещё не проверена.

В sea-short снова появилась фраза «В благодарность кит помогает Нике».
Карточка описывает последовательность событий, а не мотив. Такой же факт
ранее отклонялся у v3, поэтому критерий не ослаблялся: rubric_passed=true,
facts_supported=false, итог не принят. Один верный числовой факт и корректная
ссылка не доказывают поддержку остальных утверждений. Даже прямой запрет
догадок в prompt не даёт гарантии фактической точности модели.

Принято 1/2; ошибок API в этой попытке нет. Условие обоих принятых ответов
для перехода к полным 20 не выполнено, полный этап не запускался. Старые
2/4 v4 и 16/20 расширения не изменялись и не объединялись с новым повтором.
Оценщик — Codex, не независимый и не слепой. Это не доказательство устранения
HTTP 503 или общей регрессии/улучшения v4; разные ошибки требуют отдельного учёта.

Python-код не менялся. 132 теста прошли, 3 интеграционных пропущены;
валидация прошла для 12/10, 40/20 и 40/2. Подготовки и trace проверены
по хешам, данные и архивы сверены с HEAD. v2 остаётся по умолчанию.

### Проверяемые цитаты вместо свободного пересказа — 26 октября 2026

Одна лишь инструкция не гарантировала отказ от неподтверждённых мотивов.
Поэтому изменён контракт экспериментального генератора: модель может
выбрать только существующие ID карточек и полных переданных фрагментов.
Текст цитаты копирует код, метаданные берутся из карточки; count, lookup
и compare_duration формируются из точных данных без запроса к модели.
Прежний AnswerGenerator и публичный Answer сохранены, режим выбирается явно.

Выдуманная цитата, дополнительный reason от модели, чужой ID и подменённый
chunk отклоняются. Нельзя удалить отрицание внутри фрагмента через выбор
произвольных символов: выбирается целый предоставленный блок. Это проверка
происхождения текста, а не гарантированная релевантность выбранного сюжета
или полнота ответа. Для длинных карточек нужный факт может не попасть
в выбранные части; смысловая приёмка по rubric остаётся обязательной.

12 новых тестов покрывают цитаты/числа, отказы, части, точные операции,
ошибки и атрибуцию режима; всего 144 прошли, 3 интеграционных пропущены.
Проверки данных прошли для 12/10, 40/20 и 40/4. Тесты grounded по-прежнему
проходят; декодер structured-ответа Gemini общий, транспорт не менялся.

В реальном эксперименте на тех же четырёх вопросах sea-short и space
получили HTTP 503, mechanical-whale принят с дословной цитатой и полной
причинной цепочкой. Count-all сформирован кодом: 40 и все 40 источников.
Из трёх вызовов Gemini успешен один; общий итог — 2/4 (50%). Сохранены
все подготовки, Recall/фильтр 100%. Это не доказательство общего улучшения
или ухудшения смысла: два ответа отсутствуют. Отдельный офлайн-пример
проверяет сборку sea-short из известного ID без выдуманного мотива;
он не считается ответом модели или новым принятым случаем.

В manifest добавлены generator_mode и renderer_version; у внешнего объекта
mode=custom, принадлежность renderer не угадывается. Данные и история
не переписывались, новых зависимостей нет, по умолчанию остаётся grounded/v2.
Следующий эксперимент — оценка нового режима на более широком наборе
при доступном API, без смешивания ошибок сервиса с фактическими ошибками.

### Исправление сюжетного LOOKUP — 26 октября 2026

Два ревью подтвердили одну первопричину: точный маршрут извлечения был
ошибочно принят за тип ответа. Планировщик использует LOOKUP для любого
узнанного названия, в том числе «Расскажи сюжет» и «Как дракон помог пекарю».
Ответ только с годом и длительностью имел правильный источник, но не
содержал запрошенного факта. Точная карточка сама по себе не гарантирует
семантической полноты готового ответа.

Выбран простой способ: для общего LOOKUP всегда сохранять метаданные и
полный дословный synopsis карточки. Он уже в точном контексте; новый парсер
или вызов Gemini не требуются. Недостаток — сюжет добавляется и при вопросе
только о длительности. Подсчёты и сравнения не менялись. Версия renderer
повышена до v2, чтобы не приписывать изменение прежнему эксперименту.

Сквозной тест через SearchService с настоящими planner/JSON-каталогом
воспроизвёл три отказа до исправления и прошёл после него. Проверены сюжет
маяка и дыхание дракона при сломанной печи, источники и отсутствие вызовов
retriever/Gemini. Четыре примера до/после включают также вопрос о длительности.
Всего 145 тестов прошли, 3 интеграционных пропущены; данные валидны для
12/10, 40/20 и 40/4. Индексы, исходные данные и исторические прогоны не
менялись; сеть не использовалась. Исходник renderer v1 сохранён отдельно
и совпадает с хешем реального предыдущего прогона.
