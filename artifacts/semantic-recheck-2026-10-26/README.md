## Метод

ожидаемым статусом, ограничениями и фактами карточек. По каждому ответу
сохранено отдельное объяснение. Программная проверка подтвердила хеши
case/trace, совпадение случаев с questions.jsonl, отдельных файлов с trace,
карточек в контексте и выдаче с catalog.json, структуру ответа и статусы.
Смысловые решения не получены поиском подстрок.

Новые [решения A](reviews-A.json) и [решения B](reviews-B.json) привязаны
к исходным хешам. Через `ReviewedSemanticJudge` и чистую функцию `summarize`
пересчитаны [метрики A](metrics-A.json) и [метрики B](metrics-B.json).
Они полностью совпали с исходными. `score_run` не вызывался, поскольку
он перезаписывает файлы прогона. [verification.json](verification.json)
фиксирует коммит проверяемого кода и SHA-256 всех исходных A/B-файлов;
их байты дополнительно сверены с HEAD.

## Оговорки для внешнего оценщика

`no-match` отвечает общей фразой «В каталоге нет подтверждения по этому
запросу». По прежнему критерию отсутствие буквального повторения «40 минут»
не мешает приёмке: фильтр сохранён, замен нет. Полный каталог отдельно
подтверждает отсутствие подходящих фильмов: минимум 52 минуты. Одна только
пустая семантическая выдача такого вывода не доказывает. Если внешний оценщик
потребует явно повторять числовое условие в ответе, оба решения изменятся:
A — 8/10, B — 9/10. Это иной критерий приёмки, а не новые исходные метрики.

Деталь, исправившая `space` в B, находится в `recommendations.reason`.
Если интерфейс показывает только `text`, пользователь её не увидит.
Текущая проверка оценивает весь контракт JSON; отдельный интерфейс не проверялся.

Для независимой оценки другой человек или отдельно выбранный оценщик должен
прочитать те же вопросы, ответы, карточки и rubric, зафиксировать трактовку
спорного случая и заполнить собственные решения. Независимая проверка пока
не проведена. Повторные API-прогоны нужны для оценки устойчивости генерации,
но в этот этап не входят.
